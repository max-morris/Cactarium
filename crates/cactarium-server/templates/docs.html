Publishing on the Cactarium

The Cactarium holds three kinds of entry, all named owner/name:

  • Packages: a git repo of thorns, versioned by its tags. The code stays in your repo.
  • Stacks: versioned thornlists. Every release pins every repo to a commit.
  • Sims: a parfile plus the exact configuration it ran on, as one .sim file.

Browsing and downloading need no account. Publishing needs one: sign in with GitHub or ORCID. A new entry is reviewed by an admin before it is public, and so is each new release of it (a pushed tag, a stack release, a new sim version): until it is approved, only you and the admins see it, and resolving a range skips it. Admins can trust users, organizations and individual entries. Anything published by a trusted user or under a trusted organization, and every new release of a trusted entry, publishes at once without review.

Versions and tracks

Tag releases v1.2.3. A repo can carry independent version lines, called tracks, as tag prefixes: mixed-precision/v1.2.3 is version 1.2.3 on track mixed-precision, written owner/pkg@mixed-precision:1.2.3. Ranges such as @mixed-precision:^1.2 never cross tracks.

The first time the Cactarium sees a tag it freezes the commit. Moving a tag afterward changes nothing here: the frozen commit keeps being served, and you and the admins are alerted. Publish a new version instead. A bad version can be yanked: still downloadable by exact version, never chosen by a range.

Manifests

A package repo commits cactarium.toml at its root:

format = 1

[package]
name = "carpetx"
owners = ["your-cactarium-name"]   # proof you control the repo
description = "CarpetX with mixed-precision grid functions"
license = "LGPL-2.1-or-later"
# contact = "https://github.com/you/CarpetX/issues"   # where to get help; default: the repo
# arrangement = "CarpetX"          # only if the thorns sit at the repo root
# thorns = ["CarpetX", "Loop"]     # default: every directory with an interface.ccl
default-track = "mixed-precision"

[tracks.mixed-precision]
description = "CCTK_REAL4/REAL2 storage"

[[fork-of]]
target = "einsteintoolkit/carpetx"

[[depends-on]]
target = "max-morris/cactus"
range = "mixed-precision:^1"

[[works-with]]
target = "max-morris/carpetx-mp"
range = "^1"

[[incompatible-with]]
target = "einsteintoolkit/et"
note = "needs the mixed-precision flesh"

[[caveat]]
thorn = "TestReal2"
note = "needs _Float16 (GCC 12 or newer)"

contact says where to go for help or to report a problem: an https:// URL (an issue tracker, a forum) or a mailto: address. Without one, the repo is the contact. Stacks take it in [stack], sims in [sim].

Thorns and their dependencies (IMPLEMENTS, INHERITS, REQUIRES, …) are read from each thorn's interface.ccl and configuration.ccl. Claims are shown and checked; nothing resolves them into a build.

A stack lives in cactarium-stack.toml, in its own small repo (a manifest repo) or alongside a package. It can be a plain thornlist, a recipe built on other stacks, or both:

format = 1

[stack]
name = "carpetx-mp-forks"
owners = ["your-cactarium-name"]
extends = ["et/et-stack@2026.5.0"]           # bases, highest priority first
# thornlist = "extra.th"                     # a plain thornlist, or sections on top of the bases
enable = ["CarpetX/TestReal4"]               # un-#DISABLE or keep a thorn
disable = ["CarpetX/PDESolvers"]
# pin-tag = "ET_2026_05_v0"                  # pin every repo that has this tag to it

[[stack.override]]                           # redirect a repo of the bases
repo = "CarpetX"
package = "max-morris/carpetx@mixed-precision:^1"   # or url = "…" and ref = "branch"

[[stack.pin]]                                # optional: fix one repo in the definition
name = "AsterX"
commit = "…40 hex digits…"                   # or tag = "v1.2", or sha256 = "…" for a download

Each tag cuts a release: the Cactarium merges the sources, applies the overrides, pins every repo and freezes the result. A repo is pinned by its own [[stack.pin]] if it has one (a tag named there must exist), else by a !REPO_COMMIT in the thornlist, else to the pin-tag if the repo has that tag, else to its base release's pin, else to the current head of the branch the thornlist names. Pinning by tag suits an Einstein Toolkit release, which tags each of its repos ET_YYYY_MM_vN; without pins, a release takes the branch heads at the moment the Cactarium reads its tag. It refuses thorn-name collisions (Cactus thorn names are global) and repos checked out from conflicting sources. Two unpinned forms exist for development: owner/stack@head puts each repo at the tip of the branch the stack names (repos the definition pins stay pinned), and owner/stack@master puts every repo at the tip of its default branch, like cactup install master.

Finding things

Search matches names, summaries, thorns and implementations. A stack or a sim is found by the thorns it builds too: searching CarpetX among stacks lists the stacks whose newest release builds a CarpetX thorn, and each thorn's page lists the packages that provide it and the stacks and sims that build it. A package that declares [[fork-of]] appears on its upstream's page, with a side-by-side comparison of the two. Signed in, Save keeps an entry on your dashboard; the count of saves is public.

Namespaces and organizations

Everything you publish lives under your Cactarium name or under an organization you belong to, such as et for the Einstein Toolkit. Anyone can create an organization and becomes its owner. Every member publishes under it and manages its entries; owners also add and remove members. A repo published under an organization lists the organization's name in its manifest's owners. From cactup, a member's API token publishes under the organization too.

The .sim format

A .sim is TOML holding the thornlist and the parfile verbatim, a pin for every repo, declared inputs and run hints. Only fully specified sims (every repo pinned, nothing dirty) can be published. Make one with cactup sim export, or cactup sim pack foo.th foo.par; read one with cactup import or cactup sim unpack.

API

Read endpoints need no token. Base URL: {{ base_url }}/api/v1.

  • GET /entries/{owner}/{name}
  • GET /packages/{owner}/{name}/versions
  • GET /resolve?req=owner/name@track:range: the best matching version, with its tag and frozen commit
  • GET /stacks/{owner}/{name}/releases/{version}, and …/head or …/master
  • GET /sims/{owner}/{name}/{version}/download
  • POST /sims/{owner}/{name} with Authorization: Bearer <token> and the .sim as the body

Every response carries an api-generation header.
