Sims

A sim is a parfile together with the exact configuration it ran on, in one .sim file: the thornlist and the parfile verbatim, a pin for every repo, the inputs the parfile needs from outside the source tree, and hints for running it. CactUp writes these files and imports them; the format itself is described in CactUp's docs on the .sim format. This page covers publishing one on the Cactarium.

Two ways to publish

  • Upload the file: on the site with Upload a sim, or from CactUp, which uses POST /api/v1/sims/{owner}/{name}.
  • From a repo: commit a cactarium-sim.toml that names the .sim file (or several) and register the repo. Each version tag then publishes the files as they are at that tag.

A sim uses one way only: once it is registered from a repo, uploads to it are refused.

cactarium-sim.toml

format = 1

[sim]
name = "bhns-gw230529-dense"
owners = ["max-morris"]
file = "sims/bhns.sim"
description = """
A black hole and neutron star merger like GW230529, at high resolution.
"""

A [sim] goes only in cactarium-sim.toml; the same repo can also carry a package or a stack in their own files.

Several sims in one entry: [sim.files]

A repo with several example runs can publish them all as one entry, released together: list them in [sim.files], a table keyed by sim name, instead of file. The manifest then needs format = 2 (a Cactarium or CactUp from before it says "upgrade" rather than tripping over the new key).

format = 2

[sim]
name = "cottonmouth-sims"
owners = ["et"]
description = "Cottonmouth's example simulations, on et/cottonmouth-stack."
tag-pattern = "sim-v{major}.{minor}.{patch}"   # released separately from the package

[sim.files]
qc0-bssnok = "examples/sims/qc0-bssnok.sim"
qc0-z4c    = "examples/sims/qc0-z4c.sim"
mag-tov    = "examples/sims/mag-tov.sim"
  • Sim names follow the rules for entry names (lowercase letters, digits, ., _ and -, at most 64 characters, not ending in . or -) and must start with a letter. Each name appears once (TOML refuses a repeated key), and two names can't point at the same file. If a file's own [sim] name differs from its key, reviewers get a warning; the key is what counts.
  • A version is one tag holding every sim the manifest lists there. Each is checked as an upload is. If one fails, the whole version is invalid, with every sim's reason: a version silently missing a sim would be worse. Review, yanking and visibility are per version.
  • The list may change between versions. A sim added at 1.2.0 exists from 1.2.0 on; one dropped at 1.2.0 stays available at its last version (see below).
  • The form is fixed. An entry that started with file keeps it, and one with [sim.files] keeps that, even when it lists a single sim: a tag whose manifest switches form becomes an invalid version, because every address would change meaning. To move from one to the other, register the new form as a new entry.
  • The entry's page shows one sim at a time, with the version's sims listed above the tabs; its description is the manifest's.
  • Uploads stay one sim per entry: [sim.files] is for sims released from a repo.

Why always name the sim: if owner/name meant "the only sim" while the list had one entry, it would silently change meaning, or break, the day a second sim is added.

Ranges choose the newest version in range that holds the sim. When a newer version in range dropped it, the answer says so and CactUp warns: with qc0-z4c listed at 1.0.0 and 1.1.0 but dropped at 1.2.0, et/cottonmouth-sims/qc0-z4c@1 is 1.1.0, flagged that 1.2.0 doesn't have it. A sim that no version in range holds is refused, naming the sims the newest version has.

A CactUp from before multi-sim entries reads owner/name/x as a thorn and can't import such sims; it can't fetch the wrong file either, since the Cactarium refuses a bare owner/name and a download without ?sim= for a multi-sim entry. Upgrade CactUp to import them.

Sims that build the repo's own package

Example sims usually pin the package they ship with, in the same repo. That works: every pin must be a registered, public package's repo, and the package entry beside the sims is one. When both are registered together, or the package is still awaiting review, a sims tag simply waits (it is left unread and tried again) until the package is public, and is then read. A pin to a commit the package's repo doesn't have yet waits the same way.

What every published sim must satisfy

These checks apply to every upload and to the file at every tag of a repo-backed sim. An upload that fails one is refused with the reason; a tag that fails one becomes an invalid version with the reason. At a tag, a pin problem that isn't a fact about the commit is tried again instead: the pinned repo's history can't be read right now, the pinned commit isn't in it yet, or its package is registered but not public yet. A tarball pin, or a pin to a repo no package was ever registered for, is a fact: the version is invalid.

  • The file is at most 1 MiB of UTF-8 text and a valid .sim. The reader is strict: unknown keys, or a format newer than the server knows, are errors.
  • It is fully specified: every [[repo]] is pinned to a commit, none was dirty when exported, and every thorn in the build comes from one of those repos. And every repo is a registered package's, the flesh included (et/cactus or a fork of it), at a commit that package's repo has: a published version's commit, or any other commit of its history. Someone downstream can then rebuild the sim from the Cactarium alone. A repo that isn't on the Cactarium is registered first, or the sim pins a fork that is; a tarball pin has no package identity and is refused.
  • The pins agree with the thornlist: the [[repo]] entries name exactly the repos the thornlist checks out, none missing and none extra.
  • Its [sim] root matches the thornlist's !DEFINE ROOT.

CactUp's cactup sim export and cactup sim pack produce files that pass; see CactUp's docs on its commands.

Warnings

Some things are worth a second look but don't block publishing. Reviewers see them, the sim's managers see them on its page under Notes for review, and the API returns them in warnings:

  • the parfile mentions machine-specific paths, such as /home/<user>, /Users/<user>, /scratch, /work/ or /project/: an @KNOB(...)@ input is the portable way;
  • the parfile needs @KNOB(name)@ but declares no [[input]] for it (a knob with a default in every use is optional and doesn't count);
  • the parfile needs an environment variable through @ENV(NAME)@, so it isn't self-contained;
  • CactUp would refuse the parfile when submitting it, because its @…@ tokens don't parse;
  • an input downloads and unpacks an archive, and perhaps edits files in it;
  • the sim has no license, so others can read it but may not know whether they may reuse it.

Paths and tokens inside parfile comments are not uses and raise no warning.

Versions

Sim versions are semantic versions, like those of packages and stacks. An upload names its version, such as 1.0.1 for a fix to 1.0.0, or, without one, becomes the next major version: 1.0.0 for the first, then 2.0.0, and so on. A repo-backed sim takes its versions from its tags. A version never changes and is never reused: publish a new one instead.

References work as for packages: owner/name@1 means the newest 1.x.x, and owner/name@1.0.1 exactly 1.0.1 (see ranges).

The stored copy of each version records its own reference in [sim] cactarium, such as "max-morris/bhns-gw230529-dense@1.0.0", or "et/cottonmouth-sims/qc0-z4c@1.0.0" for one sim of a multi-sim entry (stored as .sim format 4, so an older reader asks to be upgraded instead of reading the third part as a thorn). The thornlist and the parfile stay byte for byte as published. Download .sim on the sim's page and the API serve that stored copy, with its own sha256.

Inputs

An [[input]] declares something the parfile needs from outside the source tree, reached through a CactUp knob (@KNOB(name)@). On import, CactUp asks for a value, or downloads the input's url and checks its sha256. An archive input (unpack = true) is downloaded, verified and unpacked, may point the knob at a path inside it, and may apply text fixups. The sim's Inputs tab shows what each input does. The details are in CactUp's docs on inputs.

A sim published from its repo can also read an input from that repo: repo-file = "data/initial-data.tar.gz" names a file in the repo, which CactUp fetches at the version's commit (the commit pins it, so no sha256 is needed); it combines with unpack, path and fixups like a download. Such a file uses .sim format 3. At each tag the Cactarium checks that every repo-file is a file in the repo; a tag where one is missing becomes an invalid version, with the reason. An uploaded sim can't carry repo-file inputs, since there is no repo to read from.
