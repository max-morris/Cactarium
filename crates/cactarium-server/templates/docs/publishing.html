Publishing

There are two ways to publish. From a repo: commit a manifest, push a version tag and register the repo; from then on the Cactarium follows its tags. By upload: hand the Cactarium the stack definition or the .sim file itself, on the site or through CactUp.

KindFrom a repoBy upload
Packagecactarium.toml (reference)No: a package is a repo
Stackcactarium-stack.toml (reference)Publish a stack
Simcactarium-sim.toml (reference)Upload a sim

A stack or a sim uses one way only. Once it is registered from a repo, uploads to it are refused: a new release is a new tag.

From a repo

  1. Commit a manifest at the repo root: cactarium.toml for a package, cactarium-stack.toml for a stack, cactarium-sim.toml for a sim. A repo may carry any of the three; each becomes its own entry.
  2. List the name you publish under (yours, or your organization's) in the manifest's owners.
  3. Push a version tag: v1.0.0, or mixed-precision/v1.0.0 on a track. See Versions and tracks; a manifest can also name a different tag scheme, and when a repo carries several manifests, each follows its own.
  4. On your dashboard, choose Register a repo and paste the repo's https:// URL.

Owners: proof that you control the repo

The Cactarium never asks a forge who may push to a repo. Instead, each manifest names in owners the Cactarium users or organizations allowed to publish it. Only someone who can push to the repo can put a name there, so a manifest that names you proves that you control the repo. This works the same on GitHub, GitLab, Bitbucket or any other public host.

When you register, the name you publish under must be in the owners of every manifest being registered, as it is at the tag it is registered from. Every later tag is checked again: a tag whose manifest no longer names the entry's owner is not a version of it.

What registering does

The Cactarium looks at the manifests on the repo's default branch. For each one it finds that manifest's newest version tag, under that manifest's own tag rule (on the default track if it has one), and reads the manifest there; each becomes one entry, named after the manifest's name. (A repo whose default branch carries no manifest at all is read at its newest vX.Y.Z tag instead.) Then it reads every version tag of each entry. Each tag becomes a version: the Cactarium checks out exactly the tagged commit, reads the manifest and the files it names, and freezes the commit. Tags that already exist when you register count as published by you, which matters for review.

Registering is all or nothing:

  • Distinct names. Each manifest becomes its own entry, so two of a repo's manifests can't give the same name, and none can take a name its owner already uses; registering says so before writing anything.
  • Read first. Before anything is written, each new entry is read at its newest tag exactly as its first version will be: the manifest, the thorns, the stack's sources, every sim. If one fails, the error names the entry and the tag, and nothing is registered, not even the entries that read fine. Fix it, push a new tag, and register again. (A sim pin that can't be checked yet, such as one to a package registered in the same go, doesn't fail it: that tag simply waits.)
  • One transaction. Every new entry is created, attached to the repo and recorded in the audit log together, or none is. Once created, the entries stay even if their first check of tags runs into trouble: the registration reports it, and it shows as the last check's error on the entry's page.
  • Only what is missing. Registering a repo that already has entries adds the manifests that aren't registered yet, and leaves the others alone. They must all be under the same owner. So a repo that gains a cactarium-sim.toml next to its package is registered again to add the sims.

Registering at a tag

Without a tag, the manifests come from the default branch. When a manifest isn't there yet (say, the sims live on a release branch, or the default branch is behind), name the tag to read: the Tag field of Register a repo, or on the server's command line

just cli register --owner et <admin> --tag sim-v1.0.0 https://github.com/EinsteinToolkit/Cottonmouth

The manifests at exactly that tag are read, and only those that read the tag as one of their versions, under their own rule, are registered: that commit becomes their first version. One that follows another scheme (the package beside sims tagged sim-v1.0.0, say) isn't registered by it; check and the registration's notes name it, and registering again without --tag adds it. So for a repo none of whose manifests is registered yet, register it plainly first (the package, say), then with --tag for the manifest that isn't on the default branch.

Checking a release before you tag it

The site's operator can run a dry run of the same reading against the live site, without writing anything:

just cli check https://github.com/EinsteinToolkit/Cottonmouth --tag sim-v1.0.0
just cli check https://github.com/EinsteinToolkit/Cottonmouth --tag sim-v1.1.0 --commit main

It reports what registering would add and how each new entry's version would read, and, for every entry already on the repo, whether the tag is one of its versions (read by the entry's manifest at the tag's commit) and how it would read: cleanly, as an invalid version (with the reason), as not a version (with the reason), or waiting for something (a pinned package awaiting review, say). With --commit (a branch or a full commit id), a tag that doesn't exist yet is read as if it named that commit, so a release can be checked before it is tagged. It exits non-zero if anything would be invalid.

Repo URLs must be public https:// URLs without credentials in them. The code stays in your repo. The Cactarium keeps only what it read: the manifest, the facts in each thorn's CCL files, the README, the frozen thornlist of a stack, or the .sim file of a sim.

A tag becomes a version only when the entry's manifest at that commit reads it as one (how tags become versions); a tag without the manifest, or one its manifest doesn't read, is simply listed as not a version. A version whose release is wrong (the manifest there can't be read, a file it names is missing, the thorns or sims don't pass the checks) is still frozen, marked invalid with the reason, so it isn't fetched again on every check. Invalid versions are never served, not even by exact version. Fix it and push a new tag; or move the tag onto the fixed commit: an invalid version was never served, so when its tag moves it is read again at the new commit (recorded in the audit log). A valid version whose tag moves keeps its frozen commit and is marked "tag moved upstream".

Only facts about the tagged commit make a version invalid. When the trouble is not the commit's, the tag is left unread and tried again at every check until it can be read, and the reason shows as the last check's error on the entry's page: the repo host didn't answer, the manifest or .sim uses a newer format than this Cactarium reads yet, a repo a sim pins can't be read right now, the pinned commit isn't in that repo yet (pushed after the tag), or no public package has a pinned repo yet (not registered yet, or awaiting review). For a stack: one of its source repos couldn't be read, or doesn't have the branch or tag it names yet (a tag pushed a moment after the stack's), a stack it extends or its release isn't available yet (not registered, awaiting review, or not read yet), or a package an override names isn't registered or public yet, or has no matching version yet. For a package: a dependency on a package nobody registered yet, or with no version in its range yet, or whose newest version in range lacks a thorn needs names while a newer tag of it in range isn't read yet (the two released together, say), or while its repo can't be listed to tell: the package waits until that version is read, and is invalid only if no unread version in range is left. (Naming something of the wrong kind, a stack where a package belongs, say, is a fact.)

Waiting tags never hold up newer ones: each check reads the new tags first (of which at most ten may turn out to wait; the rest are read at a later check), then tries at most ten waiting tags. The automatic checks back off for each waiting tag, starting at five minutes and doubling up to six hours apart (starting over if the tag moves); the last check's error says when each will be tried next. Check for new tags now, the API refresh and just cli sync try the waiting tags at once, still ten at a time. Nothing is frozen until the tag can be read, so pushing the missing commit, or the package's approval, is all it takes.

Facts about the commit, on the other hand, are frozen: a malformed or unreadable manifest or .sim, a file it names that isn't there, a tarball pin, a dependency whose version in range lacks a thorn its needs names. An invalid version is never served, so an admin can read one again later (Admin, Entries, Re-read invalid version, or just cli reread <admin> <owner/name> <version>), for an entry released from its repo: if the commit reads cleanly now (the dependency has since published a version in range with the thorns needs names, say), the version becomes valid and is reviewed like a newly pushed tag; if another tag names exactly that version (the real v1.0.0 beside an old bare 1.0.0 that took the version), it is read from that tag when the frozen one still fails; if the tag turns out not to be the entry's at all (see tags that aren't the entry's), the invalid version is removed. Curated packages use re-apply instead.

New tags: polling, webhooks and "Check for new tags now"

The Cactarium finds later tags in three ways:

  • Polling. It checks every registered repo for new, moved and deleted tags on a fixed interval, every four hours unless the site is configured otherwise.
  • A webhook. On a package's page, people who manage it find a payload URL and a secret under Manage, Webhook for instant updates. On GitHub, add them under Settings, Webhooks, with content type application/json and "Just the push event"; each push then makes the Cactarium check the repo at once. GitLab ("Tag push events", with the secret as the token) and Bitbucket use the same URL with gitlab or bitbucket in place of github, as in /hooks/gitlab/…. A repo that carries several entries needs only one hook, any entry's: a delivery checks every entry on the repo.
  • Check for new tags now. This button, in the Manage box of a package or a repo-backed stack, runs the same check on demand. Scripts and CactUp can call POST /api/v1/packages/{owner}/{name}/refresh with an API token (see the API).

One check reads at most 50 new tags; the rest follow on the next check. If a check fails, the Manage box shows why.

How tags become versions

A repo can carry a package (cactarium.toml), a stack (cactarium-stack.toml) and sims (cactarium-sim.toml), each its own entry. The rule that turns tags into versions is simple, and it is the same for every entry:

A tag is a version of an entry exactly when the entry's manifest file is in the tag's commit, and that manifest's own rule reads the tag as a version.

"Its own rule" is the manifest's tag-pattern if it has one, else the standard form, plus its own since if it has one. The standard form is vX.Y.Z (the v is optional, so a bare 1.2.3 counts), pre-releases such as v2.0.0-rc.1, and track/vX.Y.Z on a track. The manifest must also name the entry and list its owner in owners.

So every tag is read by the manifest in its own commit. There is no setting kept on the Cactarium that a tag must match, nothing to switch: a manifest that adds, changes or drops its tag-pattern changes how the tags of the commits that carry it are read, and never touches any other tag. Old versions stay exactly as they are.

No tag-pattern: every kind shares the standard tags

When none of a repo's manifests gives a pattern, they all read the same tags, and one tag releases every kind the repo carries at that commit, each read from its own manifest:

cactarium.toml          [package] name = "cottonmouth"
cactarium-stack.toml    [stack]   name = "cottonmouth-stack"
cactarium-sim.toml      [sim]     name = "cottonmouth-sims"

git tag v1.2.0   →   et/cottonmouth@1.2.0, et/cottonmouth-stack@1.2.0 and et/cottonmouth-sims@1.2.0

A kind whose manifest isn't at that commit simply has no version there. So a repo that adds its sims manifest at v1.3.0 gets sims versions from v1.3.0 on, and the older tags are listed as "no cactarium-sim.toml": no since is needed for that (though one is honored when a manifest gives it).

A kind with a tag-pattern follows only its pattern

To release one kind on its own schedule, give its manifest a tag-pattern. From the commits that carry that manifest on, that kind reads only the tags matching its pattern; the kinds without a pattern keep reading the standard tags. A tag a pattern reads is that kind's own even when the standard form would read it too: with tag-pattern = "{major}.{minor}.{patch}" in the package's manifest, a bare 2.0.0 tag is the package's, and the sims beside it (with no pattern) list it as "max/x's release: its tag-pattern {major}.{minor}.{patch} reads 2.0.0" instead of taking it. Declaring the standard form itself, tag-pattern = "v{major}.{minor}.{patch}", is the same as declaring none: it shares the vX.Y.Z tags with the others (it only leaves out tracks, bare numbers and pre-releases), and claims nothing.

Cottonmouth's sims: from shared tags to their own, with no admin step

Cottonmouth's example sims start out sharing the package's tags: cactarium-sim.toml has no tag-pattern, so the release tag v2026.5.0 releases et/cottonmouth@2026.5.0 and et/cottonmouth-sims@2026.5.0 together, and v2026.5.1 both again.

Then a sim needs a fix and the package doesn't. Add the pattern to the sims manifest, in the same commit as the fix or before it, and tag:

# cactarium-sim.toml, from this commit on
format = 2

[sim]
name = "cottonmouth-sims"
owners = ["et"]
tag-pattern = "sim-v{major}.{minor}.{patch}"

[sim.files]
qc0-z4c = "examples/sims/qc0-z4c.sim"
mag-tov = "examples/sims/mag-tov.sim"

git tag sim-v2026.5.2   →   et/cottonmouth-sims@2026.5.2 (the package has no version there)
TagCommit's sims manifestet/cottonmouth (no pattern)et/cottonmouth-sims
v2026.5.0, v2026.5.1no patternversionsversions (kept as they are)
sim-v2026.5.2sim-v{…}not a versionversion 2026.5.2
v2026.6.0 (a later package release)sim-v{…}versionnot a version: its pattern doesn't read it

Nobody switches anything on the Cactarium: the tag sim-v2026.5.2 is read by the manifest in its own commit, which says sim-v. Number the new scheme's versions above the old ones (here 2026.5.2 after 2026.5.1): a new version that sorts below a version taken from a different tag form is flagged for reviewers, because ranges keep choosing the higher one. To go back to shared tags later, drop the pattern; the tags of the commits without it read the standard form again.

A later manifest that drops its pattern

It affects only the tags of the commits that carry it. Say the sims followed sim-v tags and a later commit drops the pattern: sim-v1.3.0 on that commit is not a version (the manifest there reads the standard form, which doesn't read sim-v1.3.0); v1.3.0 on that commit is a sims version (and the package's too, if the package has no pattern); sim-v1.2.0 on an older commit stays the version it was.

Kinds with the same pattern share its tags

Two manifests giving the same tag-pattern share those tags, just as manifests without one share the standard tags. With tag-pattern = "rel-{major}.{minor}.{patch}" in both cactarium-stack.toml and cactarium-sim.toml, and none in cactarium.toml, the tag rel-2.0.0 releases the stack and the sims at 2.0.0, and v1.1.0 releases only the package.

Never sim/v…, never -sims

Don't tag a kind's releases sim/v1.0.0 (or stack/v…). A slash is how a tag names a track: under the standard form, sim/v1.0.0 is version 1.0.0 on a track named sim, so every kind without a pattern on the repo (the package, typically) reads it as a release of its own, unless the sims manifest at that commit declares exactly tag-pattern = "sim/v{major}.{minor}.{patch}" (then the others leave it alone, but the tags still read as a track everywhere else). Don't use a suffix either: v1.0.0-sims is a pre-release of 1.0.0 under the standard form. Use a prefix with a dash, such as sim-v{major}.{minor}.{patch}, which the standard form doesn't read.

Several tags naming one version

Two tags can be read as the same version, by their own manifests: v1.0.0 and a bare 1.0.0, say, or rel-1.0 and rel-1.00 under rel-{major}.{minor}. One becomes the version, the others are listed as "version 1.0.0 is already another tag's". The winner is the best spelling under its own manifest's rule: the spelling the pattern itself writes (its placeholders filled in, no leading zeros), then the standard [track/]vX.Y.Z, then any other; between equals, the first by name. A version, once frozen, keeps its tag; and an invalid version can be read again from another of its tags (below).

Broken manifests and other entries' tags

A manifest that can't be read says nothing about which tags it would follow, so the Cactarium is careful with it. It takes the tag as a (invalid) version of its entry only when the rule of the entry's newest version (the standard form while it has none) reads the tag, and no other entry's manifest at that commit reads it. When the entry's newest version changes its rule (its first version, say, or a version with another pattern), the tags set aside because that rule didn't read them are examined again under the new one. When another entry's manifest at that commit is broken too, the tag is that entry's if the rule of its newest version (the standard form while it has none) reads it, and so no version here; otherwise it claims nothing, and reviewers see a note saying so. When another entry's manifest there is of a newer format than this Cactarium reads, a tag the entry would take waits (that entry might claim it); a tag the entry settles alone (no manifest of its own there, or its rule doesn't read the tag) doesn't. A manifest the Cactarium can't fetch as plain content (a symbolic link inside the repo, say) is read from a checkout, following the link as long as it stays inside the repo.

How the Cactarium reads a repo's tags

Every new tag on the repo (by name and commit) is examined once per entry: the entry's manifest is read at the tag's commit from a history-only mirror, without checking the whole tree out, and the outcome is recorded (a version to freeze, not a version with its reason, or waiting). Only a tag that is a version is then checked out in full and read like a release. A check examines at most a few hundred tags (standard spellings first, then by name), so a repo with many old tags, such as the Einstein Toolkit's, is examined over a few checks. Each tag's outcome is recorded as soon as it is examined, so a check stopped for time keeps what it examined. Tags whose manifest has to be read from a checkout (a symbolic link, or a host that doesn't serve files by id) are slower: a check reads a few dozen of them, and the next check goes on. A version is not frozen while a tag that could also be it (read by the standard form, or a pattern the entry is known to use: its newest version's, any version's, the one it was registered with, or that of a manifest already read) hasn't been examined yet, or waits; other versions are frozen meanwhile. So which tag wins a version doesn't depend on how the examining was split across checks. A dependency on an entry with tags not examined yet, or waiting tags that could be in its range, waits meanwhile. When the repo can't be read at all, nothing is recorded: the tags are examined again at the next check, and the last check's error says why. A tag that names a tree or a file instead of a commit is listed as not a version.

Registering reads each new entry at its newest tag first, as before (or at the tag --tag names); the first check after it examines all of the entry's tags.

Tags not read as versions

The entry's managers see them under Manage, Tags not read as versions, each with its reason: no manifest for this entry at that commit; its manifest follows another rule; it names another entry or doesn't list the owner; its sims form is the other one (file against [sim.files], fixed when the entry is registered); another entry on the repo reads it with its own tag-pattern; it is unreadable and no rule reads the tag; its version is already another tag's; it names a tree or a file, not a commit; or the tagged commit is too large to read. They are examined again if the tag moves.

Curated packages are different: their manifest is the overlay the Cactarium keeps, read at every tag, so its tag-pattern and since decide for all of their tags, and changing the overlay changes them (see curated packages).

By upload

Publish a stack

Publish a stack takes three things: a stack definition (what a cactarium-stack.toml would hold), optionally the stack's own thornlist, and the version to publish, such as 1.0.0, or mixed-precision:1.0.0 on a track. The Cactarium merges the sources, pins every repo and freezes the result as that version. An uploaded definition needs no owners.

For the next release, open the stack's page and choose Upload a new release: the form starts from the latest release's definition and thornlist. CactUp publishes stack releases through POST /api/v1/stacks/{owner}/{name}/releases. See Stacks for the definition.

Upload a sim

Upload a sim takes a .sim file of up to 1 MiB. The entry's name defaults to the name inside the file; type another under Publish as, or owner/name to choose the namespace too. The version is optional: without one, the upload becomes the next major version (1.0.0, then 2.0.0, and so on). The file must be fully specified and consistent; Sims lists the checks. CactUp uploads through POST /api/v1/sims/{owner}/{name}; see CactUp's docs on publishing.

Publish under

Everything you publish goes under your own name or under an organization you belong to. Once you belong to one, each form that publishes shows a Publish under choice. When you publish a repo under an organization, its manifest lists the organization's name in owners, not yours. An API token publishes under the same namespaces as its user.

Admins can also publish under a namespace that is no user's, for example a reserved name before its organization exists.

The dashboard

Your dashboard shows:

  • your entries and your organizations' entries, with their latest versions and whether they are public, pending review or hidden;
  • tag alerts: a version tag that was moved or deleted upstream (see frozen commits);
  • your organizations;
  • the entries you saved;
  • the outcome of your submissions in review, with the reviewer's notes.

Its buttons lead to Register a repo, Publish a stack and Upload a sim.

Review

An admin reviews each new entry, and each new release of it, before it is public, unless you, the organization you publish under, or the entry itself is trusted. Until then only the entry's managers and the admins see it. See Review and trust.
