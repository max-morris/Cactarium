Publishing

There are two ways to publish. From a repo: commit a manifest, push a version tag and register the repo; from then on the Cactarium follows its tags. By upload: hand the Cactarium the stack definition or the .sim file itself, on the site or through CactUp.

KindFrom a repoBy upload
Packagecactarium.toml (reference)No: a package is a repo
Stackcactarium-stack.toml (reference)Publish a stack
Simcactarium-sim.toml (reference)Upload a sim

A stack or a sim uses one way only. Once it is registered from a repo, uploads to it are refused: a new release is a new tag.

From a repo

  1. Commit a manifest at the repo root: cactarium.toml for a package, cactarium-stack.toml for a stack, cactarium-sim.toml for a sim. A repo may carry any of the three; each becomes its own entry.
  2. List the name you publish under (yours, or your organization's) in the manifest's owners.
  3. Push a version tag: v1.0.0, or mixed-precision/v1.0.0 on a track. See Versions and tracks; a manifest can also name a different tag scheme, and when a repo carries several manifests, each follows its own.
  4. On your dashboard, choose Register a repo and paste the repo's https:// URL.

Owners: proof that you control the repo

The Cactarium never asks a forge who may push to a repo. Instead, each manifest names in owners the Cactarium users or organizations allowed to publish it. Only someone who can push to the repo can put a name there, so a manifest that names you proves that you control the repo. This works the same on GitHub, GitLab, Bitbucket or any other public host.

When you register, the name you publish under must be in the owners of every manifest being registered, as it is at the tag it is registered from. Every later tag is checked again: a tag whose manifest no longer names the entry's owner is not published.

What registering does

The Cactarium looks at the manifests on the repo's default branch. For each one it finds that manifest's newest version tag, under that manifest's own tag rule (on the default track if it has one), and reads the manifest there; each becomes one entry, named after the manifest's name. (A repo whose default branch carries no manifest at all is read at its newest vX.Y.Z tag instead.) Then it reads every version tag of each entry. Each tag becomes a version: the Cactarium checks out exactly the tagged commit, reads the manifest and the files it names, and freezes the commit. Tags that already exist when you register count as published by you, which matters for review.

Registering is all or nothing:

  • Read first. Before anything is written, each new entry is read at its newest tag exactly as its first version will be: the manifest, the thorns, the stack's sources, every sim. If one fails, the error names the entry and the tag, and nothing is registered, not even the entries that read fine. Fix it, push a new tag, and register again. (A sim pin that can't be checked yet, such as one to a package registered in the same go, doesn't fail it: that tag simply waits.)
  • One transaction. Every new entry is created, attached to the repo and recorded in the audit log together, or none is.
  • Only what is missing. Registering a repo that already has entries adds the manifests that aren't registered yet, and leaves the others alone. They must all be under the same owner. So a repo that gains a cactarium-sim.toml next to its package is registered again to add the sims.

Registering at a tag

Without a tag, the manifests come from the default branch. When a manifest isn't there yet (say, the sims live on a release branch, or the default branch is behind), name the tag to read: the Tag field of Register a repo, or on the server's command line

just cli register --owner et <admin> --tag sim-v1.0.0 https://github.com/EinsteinToolkit/Cottonmouth

The manifests at exactly that tag are read, and that commit is the one that becomes the first version. Each manifest there that isn't registered yet must read the tag as one of its versions under its own rule; one that follows another scheme is refused, so register it from one of its own tags.

Checking a release before you tag it

The site's operator can run a dry run of the same reading against the live site, without writing anything:

just cli check https://github.com/EinsteinToolkit/Cottonmouth --tag sim-v1.0.0
just cli check https://github.com/EinsteinToolkit/Cottonmouth --tag sim-v1.1.0 --commit main

It reports what registering would add and how each new entry's version would read, and, for every entry already on the repo, whether the tag is one of its versions and how it would read: cleanly, as an invalid version (with the reason), as not its own, or waiting for something (a pinned package awaiting review, say). With --commit (a branch or a full commit id), a tag that doesn't exist yet is read as if it named that commit, so a release can be checked before it is tagged. It exits non-zero if anything would be invalid.

Repo URLs must be public https:// URLs without credentials in them. The code stays in your repo. The Cactarium keeps only what it read: the manifest, the facts in each thorn's CCL files, the README, the frozen thornlist of a stack, or the .sim file of a sim.

A tag whose manifest is missing or wrong still becomes a version, marked invalid with the reason, so it isn't fetched again on every check. Invalid versions are never served, not even by exact version, and stay invalid if their tag is moved later. Fix the manifest and push a new tag.

Only facts about the tagged commit make a version invalid. When the trouble is not the commit's, the tag is left unread and tried again at every check until it can be read, and the reason shows as the last check's error on the entry's page: the repo host didn't answer, the manifest or .sim uses a newer format than this Cactarium reads yet, a repo a sim pins can't be read right now, the pinned commit isn't in that repo yet (pushed after the tag), or the package for a pinned repo is registered but not public yet (awaiting review). For a stack: one of its source repos couldn't be read (a branch or tag lookup that failed, as opposed to the repo answering that it has no such branch or tag), a stack it extends exists but that release isn't available yet (awaiting review, or not read yet), or a package an override names exists but isn't public or has no matching version yet. On a repo carrying several entries, a tag without this entry's manifest is left alone too: it is most likely another entry's release. Tags waiting like this never hold up newer tags. Nothing is frozen until the tag can be read, so pushing the missing commit, or the package's approval, is all it takes.

Facts about the commit, on the other hand, are frozen: a malformed manifest or .sim, a file it names that isn't there, a tarball pin, a pin to a repo no package was ever registered for. An invalid version is never served, so an admin can read one again later (Admin, Entries, Re-read invalid version, or just cli reread <admin> <owner/name> <version>), for an entry released from its repo: if the commit reads cleanly now (the pinned repo has since been registered, say), the version becomes valid and is reviewed like a newly pushed tag; if the tag turns out not to be the entry's at all (see tags that aren't the entry's), the invalid version is removed. Curated packages use re-apply instead.

New tags: polling, webhooks and "Check for new tags now"

The Cactarium finds later tags in three ways:

  • Polling. It checks every registered repo for new, moved and deleted tags on a fixed interval, every four hours unless the site is configured otherwise.
  • A webhook. On a package's page, people who manage it find a payload URL and a secret under Manage, Webhook for instant updates. On GitHub, add them under Settings, Webhooks, with content type application/json and "Just the push event"; each push then makes the Cactarium check the repo at once. GitLab ("Tag push events", with the secret as the token) and Bitbucket use the same URL with gitlab or bitbucket in place of github, as in /hooks/gitlab/…. A repo that carries several entries needs only one hook, any entry's: a delivery checks every entry on the repo.
  • Check for new tags now. This button, in the Manage box of a package or a repo-backed stack, runs the same check on demand. Scripts and CactUp can call POST /api/v1/packages/{owner}/{name}/refresh with an API token (see the API).

One check reads at most 50 new tags; the rest follow on the next check. If a check fails, the Manage box shows why.

One repo, several entries: how tags become versions

A repo can carry a package (cactarium.toml), a stack (cactarium-stack.toml) and sims (cactarium-sim.toml), each its own entry. Every entry has its own tag rule, read from its own manifest: which tags are its versions. At each of those tags, the entry reads its own manifest file and nothing else, so one tag can be a version of one entry, of several, or of none. The rule is shown under Manage on each entry's page.

No tag-pattern: every kind shares vX.Y.Z tags

A manifest without tag-pattern follows the usual tags: vX.Y.Z, and track/vX.Y.Z on a track. When none of a repo's manifests gives a pattern, they all follow the same tags, and one tag releases every kind the repo carries at that commit, each read from its own manifest:

cactarium.toml          [package] name = "cottonmouth"
cactarium-stack.toml    [stack]   name = "cottonmouth-stack"
cactarium-sim.toml      [sim]     name = "cottonmouth-sims"

git tag v1.2.0   →   et/cottonmouth@1.2.0, et/cottonmouth-stack@1.2.0 and et/cottonmouth-sims@1.2.0

A kind whose manifest isn't at that commit simply has no version there: on a repo with several entries, a tag without an entry's manifest is not that entry's, rather than a broken version of it. So a repo that adds its sims manifest at v1.3.0 gets sims versions from v1.3.0 on, with no since needed.

A kind with a tag-pattern follows only its pattern

To release one kind on its own schedule, give its manifest a tag-pattern. That kind then follows only tags matching the pattern, and the kinds without one stay on vX.Y.Z. Cottonmouth releases its example sims separately from the package:

# cactarium-sim.toml
format = 2

[sim]
name = "cottonmouth-sims"
owners = ["et"]
tag-pattern = "sim-v{major}.{minor}.{patch}"

[sim.files]
qc0-z4c = "examples/sims/qc0-z4c.sim"
mag-tov = "examples/sims/mag-tov.sim"
Taget/cottonmouth (no pattern)et/cottonmouth-sims (sim-v{major}.{minor}.{patch})
v1.3.0version 1.3.0not one of its tags, even if the commit carries cactarium-sim.toml
sim-v1.0.0not one of its tagsversion 1.0.0, with every sim [sim.files] lists there
mixed-precision/v1.0.01.0.0 on track mixed-precisionnot one of its tags (a pattern's versions are all on the default track)

Kinds with the same pattern share its tags

Two manifests giving the same tag-pattern share those tags, just as manifests without one share vX.Y.Z. With tag-pattern = "rel-{major}.{minor}.{patch}" in both cactarium-stack.toml and cactarium-sim.toml, and none in cactarium.toml, the tag rel-2.0.0 releases the stack and the sims at 2.0.0, and v1.1.0 releases only the package.

Never sim/v…

Don't tag a kind's releases sim/v1.0.0 (or stack/v…). A slash is how a tag names a track: under the usual rule, sim/v1.0.0 is version 1.0.0 on a track named sim, so every kind without a pattern on the repo (the package, typically) takes it as a release of its own. Use a pattern with a dash or another separator, such as sim-v{major}.{minor}.{patch}, which no other rule reads.

A tag counts only if the manifest inside agrees

The rule an entry keeps picks its candidate tags. A candidate becomes a version only if the manifest inside that tag reads the tag the same way, under its own tag-pattern. This is what keeps a later change in a manifest from pulling an entry onto another kind's tags. Say cottonmouth-sims follows sim-vX.Y.Z, and a later commit drops tag-pattern from cactarium-sim.toml:

  • the next sim-v1.3.0 tag is still a candidate for the sims, but the manifest inside follows vX.Y.Z now and doesn't read sim-v1.3.0 at all, so the tag is not the entry's: it is recorded as such, never frozen, and its rule is not adopted;
  • the sims keep following sim-vX.Y.Z; the package's v tags never become sims versions behind anyone's back.

Registering checks the same thing: each new entry's manifest must read the tag it is registered from as one of its versions.

Tags that aren't the entry's

A candidate tag is recorded as not this entry's instead of becoming an invalid version when the manifest inside reads it under another rule (above), or when the repo carries other entries and the tag has no manifest for this one: it is another kind's release, or from before this kind's manifest existed. The entry's managers see these tags, with the reason, under Manage, Tags that aren't this entry's. They are judged again if the tag moves, and when the entry's tag rule is re-read. A repo with a single entry keeps the old behavior: a tag without its manifest is an invalid version, which is what since is for.

Switching schemes

Because a tag never changes an entry's rule on its own, switching schemes (adding, changing or removing a tag-pattern) is explicit:

  1. Change tag-pattern in the manifest, and commit it.
  2. On the entry's page, under Manage, Switch tag schemes, choose Re-read tag rule: from the default branch, or, when the new manifest isn't there yet, from a tag that carries it (which must be one of its versions under the new rule). Admins have the same button on Admin, Entries, and the operator has just cli reread-rule <user> <owner/name> [--tag <tag>].
  3. The entry follows the new rule from then on; tags recorded as not its own are judged again under it.

Number the new scheme's versions above the old ones. A new version that sorts below a version taken from a different tag form (a new v1.1.5 under an earlier sim-v1.2.0, say) is flagged for reviewers, because ranges keep choosing the higher one. A new version's manifest can move since on its own; only the tag form needs the re-read.

By upload

Publish a stack

Publish a stack takes three things: a stack definition (what a cactarium-stack.toml would hold), optionally the stack's own thornlist, and the version to publish, such as 1.0.0, or mixed-precision:1.0.0 on a track. The Cactarium merges the sources, pins every repo and freezes the result as that version. An uploaded definition needs no owners.

For the next release, open the stack's page and choose Upload a new release: the form starts from the latest release's definition and thornlist. CactUp publishes stack releases through POST /api/v1/stacks/{owner}/{name}/releases. See Stacks for the definition.

Upload a sim

Upload a sim takes a .sim file of up to 1 MiB. The entry's name defaults to the name inside the file; type another under Publish as, or owner/name to choose the namespace too. The version is optional: without one, the upload becomes the next major version (1.0.0, then 2.0.0, and so on). The file must be fully specified and consistent; Sims lists the checks. CactUp uploads through POST /api/v1/sims/{owner}/{name}; see CactUp's docs on publishing.

Publish under

Everything you publish goes under your own name or under an organization you belong to. Once you belong to one, each form that publishes shows a Publish under choice. When you publish a repo under an organization, its manifest lists the organization's name in owners, not yours. An API token publishes under the same namespaces as its user.

Admins can also publish under a namespace that is no user's, for example a reserved name before its organization exists.

The dashboard

Your dashboard shows:

  • your entries and your organizations' entries, with their latest versions and whether they are public, pending review or hidden;
  • tag alerts: a version tag that was moved or deleted upstream (see frozen commits);
  • your organizations;
  • the entries you saved;
  • the outcome of your submissions in review, with the reviewer's notes.

Its buttons lead to Register a repo, Publish a stack and Upload a sim.

Review

An admin reviews each new entry, and each new release of it, before it is public, unless you, the organization you publish under, or the entry itself is trusted. Until then only the entry's managers and the admins see it. See Review and trust.
