Review and trust

Anyone who signs in can publish, so an admin looks at what is new before it goes public, unless someone trusted vouches for it.

What is reviewed

  • New entries: a new package, stack or sim.
  • Every new release of a public entry: a newly pushed version tag, an uploaded stack release, a new sim version.

While an entry is itself waiting for review, its releases wait with it and are published when it is approved. Tags that already exist when a repo is registered count as published by the person registering it, so they are reviewed, or not, according to that person's trust. A tag found later by polling or a webhook has no publishing user; the trust of the entry and its owner decides.

What pending means

A pending entry or release is hidden. Only the entry's managers (its owner, the members of the organization it belongs to) and the admins see it, marked "pending review" or "awaiting review". For everyone else it doesn't exist yet: it isn't listed or searchable, the API doesn't serve it, no range chooses it, and no stack can use it as a base.

You can follow your submissions on your dashboard, which lists each one's status and the reviewer's note.

Approve, request changes, reject

A reviewer sees the manifest or definition, the thorns and their CCL facts, the README, the claims, the frozen thornlist of a stack and what changed since its last release, a sim's warnings, and a checklist (for a package: a license, a README naming a maintainer, documentation, tests, thorn names that don't clash). Then they decide:

  • Approve: the entry or release is published.
  • Request changes (new entries only): the reviewer's note says what to change. The entry's page shows the note to its managers; once you've made the changes, I've made the changes puts it back in the queue.
  • Reject: it stays hidden, and its managers see the note.

A release can't get "changes requested", because a release never changes. To ask for a fix, the reviewer rejects it with a note, and the owner publishes a new version. A rejected release stays hidden for good.

Trust

Trust lets publishing skip review. Three kinds of thing can be trusted:

TrustedSkips review for
A userthe entries they create and every release they publish, and every new release of entries under their name. Admins count as trusted.
An organizationentries created under it, and every new release of its entries.
An entryevery new release of that entry.

In full: a new entry is public at once when the user creating it is trusted (or an admin), or when it goes under a trusted user's or a trusted organization's name. A new release is published at once when the entry, its owner (user or organization), or the user publishing it is trusted. Anything else waits for review.

Trusting someone later doesn't approve what is already waiting. Trust is also not the verified badge: an admin grants that per entry as a public signal, and it skips nothing.

Who grants trust

By default only the superadmin grants or withdraws trust. The superadmin can let any admin do it, with the site setting Who can mark users, organizations and entries trusted under Admin, Site.

Whoever may grant trust does it from Admin, Users (for a user), Admin, Entries (for an entry), the organization's page (for an organization), or the review form, which has boxes to trust the submitter or the entry along with the decision. The site's operator can also run just cli admin trust <name> with a username, an organization or an owner/name.

Hidden entries

Admins can also hide an entry that is already public. A hidden entry looks like a missing one to everyone but its managers and the admins, and its repo is no longer checked for new tags. The repos of banned users aren't checked either.
