HTTP API

CactUp talks to the Cactarium through a small JSON API. Its base URL is {{ doc.base_url }}/api/v1. Reads need no token and see public entries and published versions only: a pending or hidden entry answers 404, like a missing one. Writes need an API token.

The response bodies are the Rust types in api.rs of the shared crate cactup-ecosystem-common, which the server and CactUp both compile against; a stack release is FrozenStack in its stack.rs. Field names are kebab-case. The crate's docs/api.md is the reference both sides follow.

Response headers

HeaderMeaning
api-generationOn every response under /api/v1; currently 1. A client that sees a generation it doesn't know should ask its user to upgrade rather than guess.
x-cactarium-unpinnedtrue on every @head or @master response: the body is not a release and its repos are not all pinned.
x-cactarium-untrustedOn every @head or @master response, and on a package read at a commit no version froze: true when the entry isn't trusted (neither it nor its owner), whose branch tips nobody reviewed, else false. Releases don't carry it.
x-cactarium-include-unreviewed (request)true asks for what awaits review too, on every read: resolution, entries, version lists and commits, stack releases, sim downloads, the lookup and providers. With an admin's token in Authorization, they also serve releases awaiting review (never rejected or invalid ones) and entries awaiting their first review. Without one, releases awaiting review of public entries are served when the site serves unreviewed code (its untrusted-tips setting is allow); otherwise the header is ignored. Each version awaiting review says "review": "pending" (absent once approved). CactUp sends the header for --risky-allow-untrusted-artifacts; the review page shows the command.
x-cactarium-unreviewedtrue on an answer that serves something awaiting review (only ever to a request that asked, as above).
x-cactarium-contactOn every stack release response, @head and @master included: where to go for help with the stack, its declared contact, else its repo. Empty when it has neither.
x-sha256On a sim download: the file's sha256, in hex.

Errors and limits

An error is a non-2xx status with a body like

{"error": {"code": "not-found", "message": "Not found"}}

The code is one of not-found, unauthorized, forbidden, bad-request, conflict, rate-limited or internal, and the message is meant to be shown to the user as it is. Some endpoints are rate-limited per client address, per minute (a few per user, per hour); past the limit they answer 429 with rate-limited and a Retry-After header: the whole seconds until the client may try again. A refused request isn't counted, so one sent after that wait gets through.

Read endpoints

GET /resolve?req=owner/name[/sim]@range[&kind=package|stack|sim]

The best version of a package, stack or sim matching a reference: the highest published, non-yanked, valid version in the range, on the track the range names. An exact request such as @1.2.3 also reaches a yanked version, which the response marks "yanked": true. For a package, @head and @master resolve to its default branch's tip, with the unpinned headers; for a stack they are refused (fetch releases/head instead).

With kind, an entry of another kind is a 400 saying what it is (owner/name is a sim, not a package), before anything else about the reference is read; a client that only takes one kind can send it. Without it, a bare owner/name of a multi-sim entry is a 400 that says it is a sim entry and lists its sims.

Response: Resolved. slug is the exact reference chosen, kind is package, stack or sim, url is the repo to fetch from (for an entry registered from a repo), contact is the version's declared contact or the repo, and the fields of VersionInfo follow inline.

curl -G {{ doc.base_url }}/api/v1/resolve --data-urlencode 'req=max-morris/carpetx@mixed-precision:^1'
{
  "slug": "max-morris/carpetx@mixed-precision:1.4.0",
  "kind": "package",
  "url": "https://github.com/max-morris/CarpetX.git",
  "contact": "https://github.com/max-morris/CarpetX/issues",
  "version": "mixed-precision:1.4.0",
  "track": "mixed-precision",
  "tag": "mixed-precision/v1.4.0",
  "commit": "3f2c9e1a00112233445566778899aabbccddeeff",
  "tree": "…",
  "yanked": false,
  "yank-reason": null,
  "state": "ok",
  "curated": false,
  "published": 1762300800
}

state is ok, invalid, tag-moved (the tag points elsewhere upstream now; the frozen commit still counts) or upstream-missing. published is in Unix seconds. tag is null for versions named by commit and for uploads.

One sim of a multi-sim entry ([sim.files]) is always named: owner/name/sim@range. The answer is the newest version in range that holds the sim, and carries two more fields, absent otherwise:

  • sim: the sim chosen, to pass to the download as ?sim=;
  • newer-without-sim: when a newer version in range no longer holds the sim (it was dropped), that version; CactUp warns. Absent when the chosen version is the newest in range.
curl -G {{ doc.base_url }}/api/v1/resolve --data-urlencode 'req=et/cottonmouth-sims/qc0-z4c@1'
{
  "slug": "et/cottonmouth-sims/qc0-z4c@1.1.0",
  "kind": "sim",
  "url": "https://github.com/EinsteinToolkit/Cottonmouth",
  "contact": "https://github.com/EinsteinToolkit/Cottonmouth",
  "sim": "qc0-z4c",
  "newer-without-sim": "1.2.0",
  "version": "1.1.0",
  "track": null,
  "tag": "sim-v1.1.0",
  …
}

A bare owner/name for a multi-sim entry is a 400 listing its sims (owner/name/qc0-z4c, …); owner/name/x for a one-sim entry is a 400 too; a sim no version in range holds is a 400 naming the sims the newest version has. For a package the third part is a thorn (owner/pkg/Thorn@range), checked against thorn-name rules, and the answer is the package's.

GET /entries/{owner}/{name}

Any entry. Response: EntryInfo: its slug, kind, summary, whether it is verified or curated, its repo and contact, its number of saves (hearts), its tracks (the default track as "") and the labels of its published versions (valid ones, yanked included). For a multi-sim entry, sims lists the sims of its newest version (absent otherwise).

GET /packages/{owner}/{name}/versions

Every published version of a package, newest first within each track, yanked and invalid ones included and marked. Response: PackageVersions, whose versions are PackageVersions: the VersionInfo fields, the repo url, the thorns (ThornInfo: arrangement, thorn, the repo-path to write in a thornlist, and the CCL facts) and the claims (ClaimInfo: kind, target, range, note).

GET /packages/{owner}/{name}/versions/{head|master|commit}

With a commit id (full, or abbreviated to at least 7 hex digits) in place of head/master: the version frozen at that commit if there is one (a normal PackageVersion; when several froze it, the newest on the default track, else the newest on any track, ties to the track name first), else the package read at that commit, its version the commit id, with x-cactarium-untrusted and the same trust rule as tips (see commits). /resolve?req=owner/pkg#<commit> answers the same way, with the full id in its slug (owner/pkg#<full commit>); owner/pkg@<hex> is read as a commit only when it names no version, range or track. An ambiguous or unknown prefix is a 400. A reading at a full commit id that was read before is answered from the cache without counting against the limit below; tips, abbreviated ids and readings not cached yet count.

The package at its default branch's tip, read now, in the shape of one PackageVersion whose version is head or master (the two mean the same for a package). Carries x-cactarium-unpinned and x-cactarium-untrusted. For an untrusted package it answers 403 unless the site allows untrusted branch tips. Limited to 12 requests a minute.

POST /packages/read

Many packages, each at a commit, in one request: each item is answered as GET /packages/{owner}/{name}/versions/{commit} answers it, so a client learns a whole base's claims, fork-of and dependencies at once. No token; x-cactarium-include-unreviewed counts as on every read. The body is a ReadRequest: at most 200 items, each a package (owner/name) and a full commit (40 or 64 lowercase hex digits), no pair twice; anything else is a 400 for the whole request. The request counts once, however many items it has, against the limit of 12 reads made now a minute; a 429 (with Retry-After) refuses it whole.

{"items": [{"package": "et/carpet", "commit": "3f2c9e1a00112233445566778899aabbccddeeff"}]}

The answer, ReadAnswer, has one item per pair, in request order: the package and commit as asked, a status, and with ok the version the single read answers (the version that froze the commit, as this request may be served it, or the package read now, its version the commit id), with untrusted and unreviewed saying what the single read's x-cactarium-untrusted and x-cactarium-unreviewed would. Any other status comes with the single read's error message:

StatusWhen
okread (or the version that froze the commit)
forbiddena commit no version froze, of a package that isn't trusted, on a site that doesn't serve untrusted code
not-foundno such package (or none this request may see), or no such commit in its repo (is it pushed?)
bad-requestthe package at that commit can't be read: an invalid manifest, a thorn problem
upstreamthe package's repo host couldn't be reached, or didn't send the commit in time; try again later
not-readnot read this time: the request's budget for fetching from repo hosts ran out, or the read would take too long. Ask again, or read that one alone. A client reads a status it doesn't know as not-read

What is read now comes from the Cactarium's own copy of the package's repo history, kept current at every package's default-branch tip, and shares the single reads' cache, so a commit read before, or a base at the packages' tips, costs no fetch from a repo host. The answer comes within 20 seconds: an item not done by then is not-read (still being read; ask again shortly) and goes on in the background, so asking again a little later finds it. Items are read eight at a time, in request order. Fetching from repo hosts is bounded across all requests (16 items at once, 32 readings under way in all): an item that finds no room is not-read at once.

GET /stacks/{owner}/{name}/releases

A stack's published releases. Response: StackReleases: the slug and a list of VersionInfo.

GET /stacks/{owner}/{name}/releases/{version}

One release, by its exact version: 1.2.0, or track:1.2.0. A yanked release is still served. Response: FrozenStack: format, the exact stack reference, root, the thornlist (filename and verbatim text), one repo entry per repo with its pin, and the recipe (the definition) it was cut from. Carries x-cactarium-contact.

With head or master in place of the version, the response is the stack's unpinned form, resolved now: repos left on a branch tip have no commit, and stack ends in @head or @master. It carries x-cactarium-unpinned and x-cactarium-untrusted, answers 403 for an untrusted stack unless the site allows untrusted branch tips, and is limited to 12 requests a minute.

GET /sims/{owner}/{name}/{version}/download[?sim=<sim>]

One sim version's .sim file, by its exact version, such as 1.0.0; a yanked version is still served. The body is the stored file (content type application/toml), with its sha256 in x-sha256.

For a multi-sim entry, ?sim= names the sim and is required (without it the answer is a 400 naming the version's sims); the body and x-sha256 are that sim's own, stamped cactarium = "owner/name/sim@X.Y.Z" in .sim format 4. A one-sim entry refuses ?sim=. A client caching downloads keys them by sim too (for example simfiles/<owner>/<name>/<sim>/<version>.sim).

A stack release's repos, and those of a sim stored since pins carry labels, say which package version each pin is: cactarium = "owner/pkg@X.Y.Z" when a published version of the package whose repo it is froze that commit (see labels). A stack's are filled in when it is served; a stored sim is served byte for byte as it was stored.

POST /lookup

Which package each pinned commit is, and whether each pinned download was reviewed: what CactUp asks before it exports or publishes a sim. No token. The body is a LookupRequest: pins (a repo url and a full commit, 40 or 64 lowercase hex digits) and downloads (a url and a sha256), at most 1000 together, each URL at most 2048 bytes. Limited to 60 requests a minute.

{"pins": [{"url": "git@github.com:EinsteinToolkit/Carpet.git", "commit": "3f2c9e1a00112233445566778899aabbccddeeff"}],
 "downloads": [{"url": "https://example.org/id.tar.gz", "sha256": "…"}]}

The answer, LookedUp, has one entry per pin and per download, each list in request order. A pin's URL matches a registered package's repo by the shared key (url::normalize_repo_url: scheme, login, default port, .git and slashes don't count, nor the host's case), else, on GitHub, GitLab and Bitbucket, by the same path in another case. Each pin says the package (or null), the version that froze the commit (among the versions the request may be served, yanked ones included; when several did, the newest on the default track, else on any track), whether the package is a flesh (exact for a commit a version froze; for any other, the newest version's value, a hint), that version's fork-of targets (empty for a commit no version froze), commit-known (true when a version froze the commit or the package's repo has it, false when it doesn't, null when there is no package or its history can't be read just now) and "review": "pending" for a version awaiting review. A download says its review: pending, approved, rejected, or null when it was never submitted.

GET /providers?implements=…

The thorns of published packages that meet one CCL requirement: exactly one of implements (an implementation they IMPLEMENTS), capability (one they PROVIDES), function (an aliased function they PROVIDES FUNCTION) thorn (a thorn of that name), a CCL name ([A-Za-z0-9_]+, compared case-insensitively), or include (a header they provide with INCLUDE[S] ...: x IN it, such as TP_Guts.h: letters, digits, _, . and -, not starting with .). Only the newest valid, unyanked version of each package and track the request may be served is searched. Response: Providers, a list of package, version, arrangement and thorn (with "review": "pending" for a version awaiting review).

{"providers": [{"package": "et/carpet", "version": "2026.5.1", "arrangement": "Carpet", "thorn": "CarpetSlab"}]}

API tokens

Write endpoints take a token in the Authorization header:

Authorization: Bearer cactarium_…

Create tokens on your Settings page, under API tokens: give each a name and a lifetime from 1 to 366 days. A token is shown once, when it is created, and stored only as a hash; revoke it there at any time. Every token has the scope publish: it publishes sims and stack releases, and refreshes repos, as its user, under the user's own name and the organizations the user belongs to. The site's operator can also create one with just cli token <username> (90 days unless --days says otherwise).

A missing, expired or revoked token, or one whose user is banned, gets 401.

Token endpoints

The publishing endpoints answer with what was created or found. Published holds the new version's exact slug, the url of its page on the site, its visibility (public, or pending while the entry or the release waits for review), and warnings a reviewer will look at.

POST /sims/{owner}/{name}

Publishes the request body, a .sim file, as a version of owner/name, creating the sim if it is new. The optional query parameter version=X.Y.Z names the version; without it the upload becomes the next major version. The file must pass the checks; the warnings come back in warnings. Answers 409 if the version exists or owner/name is not a sim, 403 for a namespace you can't publish under, and 400 for a repo-backed sim or a file that fails a check. Limited to 20 requests a minute. Response: Published.

curl -X POST -H "Authorization: Bearer $TOKEN" --data-binary @bhns.sim \
  '{{ doc.base_url }}/api/v1/sims/max-morris/bhns-gw230529-dense?version=1.0.1'

POST /stacks/{owner}/{name}/releases

Cuts a release of an uploaded stack, creating the stack if it is new. The body is a JSON ReleaseRequest: the definition (the cactarium-stack.toml text, whose [stack] name must be {name}), the stack's own thornlist or null, and the version, 1.2.0 or track:1.2.0. Refused for a repo-backed stack or a version that exists. Limited to 10 requests a minute. Response: Published.

{
  "definition": "format = 1\n\n[stack]\nname = \"carpetx-mp\"\nextends = [\"et/carpetx-stack@1.0.0\"]\n",
  "thornlist": null,
  "version": "1.0.0"
}

POST /packages/{owner}/{name}/refresh

Checks the entry's repo for new, moved and deleted tags now, like Check for new tags now on the site. The token's user must manage the entry. Despite the path, it works for any entry registered from a repo. Limited to 10 requests a minute. Response: Refreshed: the slug, how many versions this check added (new-versions), and how many of the entry's versions wait for review (awaiting-review).

POST /repos

Registers the manifests a repo carries as entries, exactly as Register a repo does: a preview first, then a confirm. The body is a RegisterRequest: the repo url; optionally the tag to start from, the owner (an organization of yours; else your own name), only (manifest names: register just those entries) and dry-run (say what registering would do, writing nothing). A dry run answers with the preview and an expect fingerprint; sent back with the same request, it registers exactly what the preview showed, or nothing: 409 when the repo or the entries on it changed since (preview again). Without expect, it registers what a preview would show now.

The answer, Registered, lists every entry on the repo with its status: new (registered, or would be), existing, skipped (left out by only, or the tag isn't one of its versions), needs-tag (not every tag could be read: name the tag to start from) or fails (it can't be registered as it is, so nothing is; a registration with one answers 400), and why, in note. A new entry's review is pending (its versions wait for an admin's review) or approved; once registered it has its page's url, the versions its first check stored (new-versions), those awaiting review (awaiting-review) and what that check reported (warnings, such as a version that waits for a dependency). A repo with nothing to add answers 200 with every entry existing. Previews and registrations count against the same hourly limit per user as on the site.

{"url": "https://github.com/EinsteinToolkit/Cottonmouth", "tag": "v2026.5.1", "owner": "et", "dry-run": true}

GET /whoami

Who the token belongs to: {"user": "max", "orgs": ["et"], "admin": false}, the username (also your own namespace), the organizations you may publish under, and whether you are an admin.

POST /downloads

Submits a download for review: a file a sim pins by its sha256 (a tarball component, or an [[input]]'s download), so a sim that pins it can be published. The body is a DownloadSubmission: the url, the content's sha256 and an optional note for the reviewer (what it is, why it can be trusted). The answer comes at once: DownloadReview, {"id": 7, "review": "pending"}. The Cactarium then fetches the URL once in the background (https only, public hosts only, at most 2 GB and 15 minutes) and checks the sha256, keeping no copy; only a download verified so can be decided by an admin, and a trusted user's or an admin's is approved as soon as it is verified. Until then, and when the fetch fails (the content has another sha256, the host doesn't answer), the lookup says pending. A download submitted before (same URL and content) answers 409 with an error body that also carries its id and review, its message saying where its verification stands (being verified, verified, or why the server couldn't verify it). One whose fetch failed is tried again at once, and its 409 says why the last try failed (most often the file's sha256 is X, not Y). A sim refused over a download says the same: that it is being verified, or why the server couldn't verify it. A URL no fetch could read (not http or https) is a 400. Limited to 10 an hour per user, and 3 being fetched at once. CactUp's cactup download submit <url> calls it.

Outside the API

The site's own downloads, /{owner}/{name}/{version}/download.sim for a sim (with ?sim= for one of a multi-sim entry) and /{owner}/{name}/{version}/download.th for a stack's frozen thornlist, serve plain files. A multi-sim entry's pages take ?sim= too: /{owner}/{name}/{version}?sim=qc0-z4c. Forge webhooks go to /hooks/{github|gitlab|bitbucket}/{entry-id}, and a verified delivery checks every entry on the same repo; see Publishing.
