Stacks: cactarium-stack.toml

A stack is a versioned thornlist. Each release pins every repo it checks out, a git repo to a commit and a download to its sha256, and then never changes, so installing the same release twice gives the same sources. The definition is a cactarium-stack.toml: in a repo, where each version tag cuts a release, or uploaded on the site, where you name each release yourself.

A repo that holds only a stack file and its thornlist is called a manifest repo. A stack file can also sit next to a package's cactarium.toml in the same repo.

Three shapes

One format covers three shapes, and none is preferred over the others:

  • Flat: a thornlist and nothing else (thornlist, no extends).
  • Recipe: extends releases of other stacks, then redirects repos and enables or disables thorns.
  • Both: bases, plus extra sections from the stack's own thornlist on top.

A definition needs a thornlist, extends, or both. A flat stack:

format = 1

[stack]
name = "carpetx-stack"
owners = ["et"]
description = "CarpetX and the thorns it needs"
thornlist = "carpetx.th"

A recipe:

format = 1

[stack]
name = "carpetx-mp-forks"
owners = ["max-morris"]
description = "The Einstein Toolkit release with mixed-precision CarpetX"
extends = ["et/et-stack@2026.5.0"]
enable = ["CarpetX/TestReal4"]
disable = ["CarpetX/PDESolvers"]

[[stack.override]]
repo = "CarpetX"
url = "https://github.com/max-morris/CarpetX.git"
ref = "mixed-precision"

[[stack.override]]
repo = "SpacetimeX"
package = "max-morris/spacetimex@mixed-precision:^1"

A stack file may also carry dependencies ([[dependency]], without needed-by) and claims ([[works-with]], [[incompatible-with]]), shown on the stack's page.

[stack]

FieldWhat it does
name
required		The entry's name, with the same rules as a package's.
ownersRequired in a repo's stack file: the users or organizations allowed to publish it, the proof that you control the repo. Unused in an uploaded definition.
descriptionWhat the stack is for. Its first line becomes the summary.
contactWhere to go for help: an https:// URL or a mailto: address. Default: the repo.
thornlistA CRL thornlist file, relative to the repo root. For a flat stack it is the whole list; with extends, its sections go on top of the bases and win over them. In an upload, paste the thornlist into its own box instead.
extendsBase releases, highest priority first. Each is an exact release, owner/stack@1.2.0 or owner/stack@track:1.2.0: not a range, not @head. A base must be public, or a stack of the same owner.
enableThorns to enable, as Arrangement/Thorn: a #DISABLED line in any source is uncommented, and a thorn a source only checks out (on its !CHECKOUT line) is built.
disableThorns to disable, as Arrangement/Thorn; they are written as #DISABLED. Some source must check the thorn out. A thorn can't be both enabled and disabled.
pin-tagPin every git repo that has a tag of this name to that tag's commit, such as "ET_2026_05_v0". See the pin order.
tag-pattern, sinceWhich tags of a repo-backed stack cut releases, as for packages and explained under tag patterns. In a repo that also carries a package, a stack without a pattern is released by the package's vX.Y.Z tags too; give it a pattern (stack-v{major}.{minor}.{patch}, never stack/v…) to release it on its own (how tags become versions).
[[stack.override]]Redirects a repo of the bases; below.
[[stack.pin]]Pins one repo in the definition itself; below.

How sources are merged

The sources, highest priority first, are the stack's own thornlist and then each base release in the order extends lists them. Components are merged by checkout location, and the first source to check out a location wins. Then enable and disable apply, then the overrides. All sources must agree on ROOT.

[[stack.override]]

An override points one repo of the bases somewhere else: a fork, another branch, or a version of a Cactarium package. Overrides need extends, and each repo can be overridden once.

FieldWhat it does
repo
required		The repo's name as the base thornlist derives it: its !NAME, else the basename of its URL. Some source must use it.
urlThe repo to check out instead.
refThe branch or tag to check out instead.
packageA Cactarium package and range instead of url and ref, such as "max-morris/spacetimex@mixed-precision:^1". The best matching version is chosen when the release is cut, and the repo is pinned to its frozen commit.

Give package, or url and/or ref, not both. An overridden repo keeps its name, and it no longer takes its base release's pin: it is pinned afresh.

[[stack.pin]]

A pin fixes one repo in the definition. Pins are optional and may cover only some repos; a release pins every repo regardless.

FieldWhat it does
name
required		The repo's name as the thornlist derives it (its !NAME, else its URL's basename). Some source must use it, and each repo can be pinned once.
commitA full commit id (40 or 64 hex digits).
sha256The sha256 of a download (an http, https or ftp component).
tagA tag, resolved to its commit when a release is cut. The tag must exist, and the repo must be a git repo.
url, refInformational: the repo's URL and branch, as a .sim's pins record them.

Each pin gives exactly one of commit, sha256 or tag.

The pin order

When a release is cut, each repo is pinned by the first of these that applies:

  1. its own [[stack.pin]];
  2. a !REPO_COMMIT in the thornlist (an override with package brings one);
  3. pin-tag, if the repo has that tag;
  4. its base release's pin, if the repo still comes from where the base had it (the same URL and branch);
  5. the current head of the branch the thornlist names, or of the default branch if it names none.

A download can't follow a branch, so pin it with a sha256 in [[stack.pin]] unless a base release already pins it. Pinning by tag suits an Einstein Toolkit release, which tags each of its repos ET_YYYY_MM_vN. Without pins, a release takes the branch heads at the moment the Cactarium reads its tag, or at the moment of the upload.

Checks

A release is refused, with the reason, when:

  • two built thorns share a name, ignoring case (Cactus thorn names are global; disable one of each pair). Thorns that are only checked out, not built, don't collide;
  • one repo is checked out from conflicting sources (different URLs, branches or commits);
  • an override, a pin or a disable names something no source has;
  • the sources disagree on ROOT;
  • a base release doesn't exist, isn't public, or isn't exact;
  • a repo can't be pinned: a missing pin tag, an unreachable repo, or a download without a sha256.

The frozen thornlist

A flat stack with nothing to change keeps its thornlist verbatim. Any other stack's thornlist is written out afresh, with a !REPO_COMMIT line for every git repo and a comment naming its sources, so the downloaded .th is pinned on its own.

The stack's page shows the frozen thornlist (with Download .th and a JSON link), the pin of every repo, what changed since the previous release on the same track, what it extends, and the definition it was cut from.

Releases: from tags or by upload

A stack gets its releases in one of two ways, never both:

  • From tags. Register the stack's repo; each version tag cuts a release from the definition at that tag. The page calls these "released by a git tag".
  • By upload. Publish a stack on the site, or through the API, and name the version yourself. The page calls these "snapshot releases". Later releases start from Upload a new release on the stack's page.

Uploads to a repo-backed stack are refused. Either way, a release is versioned like a package (semver and tracks), and a version, once published, is never reused.

@head and @master

Besides its releases, every stack has two unpinned forms, for development:

  • owner/stack@head: the definition as it stands now (for a repo-backed stack, on its default branch; for an uploaded one, the definition of its latest release). Repos keep the pins the definition gives ([[stack.pin]], !REPO_COMMIT, pin-tag) and their base releases' pins; every other repo is at the tip of the branch the thornlist names.
  • owner/stack@master: every repo at the tip of its default branch, ignoring the branches and pins the definition names, like cactup install master.

Neither is a release, and neither can be a base. Two installs a day apart can differ. Since branch tips are never reviewed, a trusted stack (the entry or its owner is trusted, see trust) always serves them, and for any other stack the superadmin's site setting Branch tips of untrusted stacks decides:

  • Refuse (the default): the Cactarium doesn't serve them at all.
  • Allow: they are served, marked untrusted; CactUp warns and asks before installing.

The API marks these responses with the x-cactarium-unpinned and x-cactarium-untrusted headers (see the API).
