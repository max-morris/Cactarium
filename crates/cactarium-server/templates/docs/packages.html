Packages: cactarium.toml

A package is a git repo of thorns. Its manifest, cactarium.toml at the repo root, says what the package is called, who may publish it, and which tags are versions. The Cactarium reads it at every version tag, so each version carries the manifest it was tagged with.

An example

format = 1

[package]
name = "carpetx"
owners = ["max-morris"]
description = "CarpetX with mixed-precision grid functions"
license = "LGPL-2.1-or-later"
contact = "https://github.com/max-morris/CarpetX/issues"
thorns = ["CarpetX", "Loop", "TestReal2", "TestReal4"]
default-track = "mixed-precision"

[tracks.mixed-precision]
description = "CCTK_REAL4/REAL2 storage; needs a mixed-precision flesh"

[[fork-of]]
target = "et/carpetx"

[[dependency]]
target = "max-morris/cactus@mixed-precision:^1"

[[dependency]]
target = "et/amrex@^2026.5"
needs = ["AMReX"]
needed-by = ["CarpetX", "Loop"]

[[works-with]]
target = "max-morris/carpetx-mp@^1"

[[incompatible-with]]
target = "et/et-stack"
note = "needs the mixed-precision flesh"

[[caveat]]
thorn = "TestReal2"
note = "needs _Float16 (GCC 12 or newer)"

Only format = 1 and a [package] with name and owners are required. The reader is strict: an unknown key, or a format newer than 1, is an error, and the tag becomes an invalid version with that message.

[package]

FieldWhat it does
name
required		The entry's name, the second half of owner/name. Lowercase letters, digits, ., _ and -, starting with a letter or a digit, at most 64 characters. Every later tag must give the same name.
owners
required		The Cactarium users or organizations allowed to publish this repo, such as ["max-morris", "et"]. This is the proof that you control the repo. It may not be empty, and it must keep naming the entry's owner: a tag whose manifest drops it becomes an invalid version.
descriptionWhat the package is. Its first line, up to 200 characters, becomes the summary shown in listings and search.
licenseAn SPDX license expression, such as LGPL-2.1-or-later or GPL-2.0-or-later OR MIT. It is recorded with each version's manifest; the Cactarium does not check it against the repo.
homepageA web page about the package, recorded with each version's manifest.
contactWhere to go for help or to report a problem: an https:// URL (an issue tracker, a forum) or a mailto: address. Shown on the package page as "Help and problems" and returned by the API. Default: the repo.
readmeThe README to show on the package page, a path relative to the repo root. It is rendered as Markdown and sanitized. Default: README.md.
arrangementThe arrangement every thorn belongs to, whatever folder it sits in: needed for a repo whose thorns sit at its root, that is itself one thorn, or whose folders don't name the arrangement (see repo layouts). A repo laid out as Arrangement/Thorn/ doesn't need it.
rootWhere the thorns are, relative to the repo root, when not at it: the folder holding the Arrangement/Thorn/ (or Thorn/) directories, such as "Auxiliary/Cactus" for Kranc. Thorns elsewhere in the repo aren't published. Default: the repo root.
thornsThe thorns to publish, by directory name, such as ["CarpetX", "Loop"]. Thorns found but not listed are left out. A repo that is itself one thorn names that thorn here. Default: every directory with an interface.ccl.
default-trackThe track the package page shows first: a track name, or "default" for the unprefixed tags. Only the page uses it: a reference without a track always means the unprefixed track. Default: the unprefixed track.
tag-patternHow release tags become versions when they aren't vX.Y.Z, such as "ET_{major}_{minor}_v{patch}". With a pattern, only the tags it matches are versions, all on the default track. See tag patterns. Default: vX.Y.Z and track/vX.Y.Z.
sinceA version, such as "2026.5.0": release tags below it aren't versions, for example releases from before the repo carried this file. Default: every release tag counts.

The Cactarium reads tag-pattern and since from the manifest on the default branch when the repo is registered. After that it takes them from the newest version's manifest, so a change takes effect once a version that carries it has been read.

[tracks.NAME]

A track is a tag prefix: mixed-precision/v1.2.0 is version 1.2.0 on track mixed-precision (see tracks). A track exists as soon as a tag uses it; this table only describes it.

FieldWhat it does
descriptionShown under the track selector on the package page. The descriptions come from the newest published manifest.

[[dependency]]

A thorn's CCL already says what it needs: the implementations it inherits from or is friends with, the capabilities and thorns it requires, the functions it requires. A dependency says where that comes from: which package, at which versions or commit. It never repeats the CCL.

FieldWhat it does
target
required		The package (or stack) depended on: owner/name for any version on its default track, owner/name@RANGE for a range such as ^2026.5 or mixed-precision:^1, or owner/name#SHA for one commit, full or abbreviated. Name thorns in needs, not here.
needsThorns of the target that are needed whatever the CCL says, such as ["CarpetX"]: to choose among packages that provide the same implementation (both Carpet and CarpetX implement Driver), or for a need the CCL can't express, such as including a header by path. Default: whichever of the target's thorns the CCL requirements resolve to.
needed-byThorns of this package the dependency is for, such as ["CarpetPETSc"]; a version whose manifest names a thorn it doesn't publish is invalid. Default: every thorn. Only a package has thorns, so a stack's dependencies can't use it.
noteFree text shown with the dependency.

The package page lists dependencies under Compatibility, and the API returns them with the claims (kind dependency).

Claims

Claims declare how the package relates to other entries. The Cactarium shows them under Compatibility on the package page and returns them from the API. They are statements, not instructions.

TableFieldsMeans
[[fork-of]]target, noteThis package is a fork of the target package, and a drop-in replacement for it at the versions target names. It is listed under Forks on the upstream's page, with a link to compare the two; see Forks as replacements.
[[works-with]]target, noteKnown to work with the target.
[[incompatible-with]]target, noteKnown not to work with the target.

Every claim takes a target as a dependency does: owner/name, owner/name@RANGE or owner/name#SHA. A range is a version range on a track, such as ^1, mixed-precision:^1.2, or a bare track name, meaning any version on that track. Without one, the claim covers every version on the target's default track. Manifests written before ranges moved into target give them as a separate range key; that still reads, but not together with a range in target. note is free text shown with the claim.

Forks as replacements

A fork says which versions of its upstream it replaces: target = "et/carpet@~2026.5" for the 2026.5 series, et/carpet#abc1234 for the one commit it was forked from, or a bare et/carpet for every version on the default track. Anything that depends on the upstream, whether a package, a stack or a sim, can then use the fork instead, as long as some published version of the upstream is both one the dependency accepts and one the fork replaces. A sim pinned to et/carpet@2026.5.1 takes a fork of ~2026.5; a dependency on et/carpet@^2027 doesn't. A dependency on one commit takes only a fork of that commit.

A fork and its upstream are never installed together: they share thorn names. A fork is used only when someone chooses it, never in place of the upstream on its own, and its own dependencies then stand in for the upstream's. Reviewers see a warning when a fork lacks thorns its upstream has, since it isn't a full drop-in then.

[[caveat]]

A note attached to one thorn, such as a platform requirement. thorn names the thorn and note says what to know. The package page marks the thorn on its Thorns tab and lists the note under Compatibility.

Repo layouts

A thorn is a directory with an interface.ccl. The Cactarium looks for thorns at three depths below the repo root (or its root) and needs to be told the arrangement when the path doesn't give it:

LayoutThe manifest needs
Arrangement/Thorn/, one or more arrangementsNothing: the path names both.
Thorn/ at the root: the repo is one arrangementarrangement = "CarpetX"
The repo root is itself one thornarrangement, and thorns naming that one thorn
Thorns below a folder of the repo (Kranc's Auxiliary/Cactus/KrancNumericalTools/GenericFD)root = "Auxiliary/Cactus", then whichever of the rows here applies from there
Folder/Thorn/, where the folder isn't the arrangement (GRHayL's implementations/GRHayLib)arrangement = "GRHayL": it wins over the folder name

The last layout is how the Einstein Toolkit's ExternalLibraries repos work: ExternalLibraries-HDF5 holds the thorn ExternalLibraries/HDF5 at its root.

format = 1

[package]
name = "hdf5"
owners = ["et"]
arrangement = "ExternalLibraries"
thorns = ["HDF5"]

Hidden directories and symbolic links are skipped. A version in which no thorn is found is invalid.

Each thorn's place in a thornlist

For each thorn, the API tells CactUp the !REPO_PATH a thornlist section that clones the package's repo should use (repo-path in the API's thorn list), derived from where the thorn sits:

  • Arrangement/Thorn/: $1/$2;
  • Thorn/ at the root: $2;
  • the repo is the thorn: ../$1-$2, so the clone must be named Arrangement-Thorn, the Einstein Toolkit's convention for ExternalLibraries.

What is read from the CCL files

From each thorn's interface.ccl and configuration.ccl, the Cactarium reads IMPLEMENTS, INHERITS, FRIEND, the functions it requires, uses and provides, and the capabilities in REQUIRES, REQUIRES THORNS, OPTIONAL and PROVIDES. They appear on the package's Thorns tab and on thorn pages, feed search, and come back from the API. The Cactarium only reads text files; it never builds or runs anything from a repo.
