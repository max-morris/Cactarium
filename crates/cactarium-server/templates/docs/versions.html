Versions and tracks

Packages, stack releases and sims are all versioned the same way: semantic versions, optionally on a named track.

Semantic versions

A version is MAJOR.MINOR.PATCH, optionally with a pre-release suffix such as 2.0.0-rc.1, which sorts before 2.0.0. Bump the major version for incompatible changes, the minor one for additions, the patch for fixes.

Version tags

In a repo, a version is a git tag: v1.2.3 (the v is optional) on the default track, or track/v1.2.3 on a track. Any other tag is ignored, not an error: ET_2026_05, v1.2, a/b/v1.2.3 and Upper/v1.2.3 are not versions. If two tags name the same version, the first one wins. A manifest can also choose a different scheme with a tag pattern.

Tracks

A repo can carry several independent version lines, called tracks, as tag prefixes. Git refs can't contain a colon, so git writes the track with a slash and the Cactarium and CactUp write it with a colon: the tag mixed-precision/v1.2.3 is version 1.2.3 on track mixed-precision, written owner/pkg@mixed-precision:1.2.3. Unprefixed tags are on the default track.

Track names start with a lowercase letter, continue with lowercase letters, digits, ., _ or -, and are at most 64 characters long. default, x, head and master are reserved. Each track has its own list of versions and its own latest version; a package's default-track only chooses which one its page shows first.

Tracks are for variants within one repo. A fork in another repo is a separate package that declares [[fork-of]].

References and ranges

What follows the @ in a reference is a version or a version range, read the way npm reads them: a full version is exact, a partial one is a range.

ReferenceChooses
owner/pkgthe newest version on the default track
owner/pkg@1.2.3exactly 1.2.3 (=1.2.3 means the same)
owner/pkg@1.2the newest 1.2.x (the same as ~1.2)
owner/pkg@1the newest 1.x.x (the same as ^1)
owner/pkg@^1.2.3the newest 1.x.x from 1.2.3 on: caret allows anything that keeps the leftmost non-zero number
owner/pkg@~1.2.3the newest 1.2.x from 1.2.3 on: tilde allows patch updates only
owner/pkg@>=1.2, <2the newest version in that interval; commas or spaces separate the comparators (>=1.2 <2), and an operator may stand apart from its version (>= 1.2 < 2)
owner/pkg@1.2.3 - 2.3.4the newest version from 1.2.3 through 2.3.4, both included; a partial upper bound covers what it names (1.2 - 2.3 is >=1.2.0, <2.4.0)
owner/pkg@^1.2 || >=2.5.0 <2.6the newest version that any of the alternatives allows
owner/pkg@mixed-precision:1.2the newest 1.2.x on track mixed-precision
owner/pkg@mixed-precisionthe newest version on track mixed-precision
owner/pkg@mixed-precision:^1 || :^2the newest 1.x.x on track mixed-precision or 2.x.x on the default track (: alone names it): each alternative has its own track, and if one names a track, every alternative must
owner/pkg@7b3a6b19… (a full commit id)the package at that commit (packages only; see commits)

With date-like versions such as the Einstein Toolkit's: et/carpetx-stack@2026.5.0 is that release, @2026.5 the newest 2026.5.N (that release line's updates), and @2026 the newest release of 2026.

The Cactarium shows a range in one normal form: >=1.2 <2 is shown as >=1.2, <2. Quote a reference with spaces, <, > or | on a command line: cactup add 'owner/pkg@>=1.2 <2'.

An alternative never crosses tracks: one without a track only ever matches the default track. A range chooses the highest matching version that is published (approved in review), not yanked and not invalid.

Release tags that aren't vX.Y.Z: tag-pattern and since

Some projects tag releases their own way. A manifest's tag-pattern says how: literal text around {major} and, optionally, {minor} and {patch}, each at most once, with no spaces; a part left out reads as 0. The Einstein Toolkit's pattern is

tag-pattern = "ET_{major}_{minor}_v{patch}"
since = "2026.5.0"

which reads the tag ET_2026_05_v0 as version 2026.5.0 and ET_2025_11_v1 as 2025.11.1. A project tagging v1.0, v1.1 uses tag-pattern = "v{major}.{minor}": v1.0 is 1.0.0. With a pattern, only the tags it matches are versions, all on the default track. since leaves out every release tag below the version it names, for example releases from before the repo carried a manifest.

Both fields exist in all three manifests ([package], [stack], [sim]) and in the overlay manifest of a curated package. Each entry keeps its own rule, read from its own manifest when it is registered: on a repo with a package, a stack and sims, each kind can follow its own tags, or share them (see how tags become versions). Afterward a new version's manifest can move since, but the tag form changes only when someone re-reads the tag rule, and a tag counts only if the manifest inside reads it the same way. Never use a slash in a kind's own tags (sim/v1.0.0): that is a track.

Frozen commits

The first time the Cactarium sees a version tag, it records the commit and tree the tag names, and from then on that version means that commit. Moving a tag afterward changes nothing here:

  • If a tag moves, the Cactarium doesn't follow it. The version is marked "tag moved upstream; the frozen commit is still served", and an alert appears on the owner's dashboard and in the admins' Tag alerts. An invalid version stays invalid, and unserved, whatever its tag does.
  • If a tag is deleted, the version is marked "tag deleted upstream" and keeps its frozen commit. If the tag comes back at the same commit, the mark goes away.

So don't move or reuse tags: publish a new version instead. Stack releases and sims are frozen the same way when they are published: their content never changes.

Yanking

Yanking marks a version as one not to use, typically a broken release. A yanked version stays downloadable by its exact version, but no range ever chooses it and listings skip it; its reason is shown with it. Nothing is deleted, and a yank can be undone.

"Exact" means a full version in a reference (@1.2.3 or @=1.2.3), a stack release or sim version fetched by its version, and a stack's extends, which names exact releases.

Whoever manages the entry can yank: the user it belongs to, any member of the organization it belongs to, and admins. On the entry's page, open the Versions tab of a package or a sim, or the Releases list of a stack, type a reason next to the version and choose Yank. Unyank reverses it.

The server's command line can do the same, acting as a user who manages the entry:

just cli yank <username> <owner/name> <version> --reason "breaks the build with GCC 14"
just cli unyank <username> <owner/name> <version>

Only the site's operator, who has a shell on the server, can run these.

A package at a commit

A package can also be named by a commit: owner/pkg#7b3a6b1, or one thorn of it, owner/pkg/Thorn#7b3a6b1. The id may be abbreviated to as few as 7 hexadecimal digits, or given in full (40, or 64 for a SHA-256 repo); the Cactarium resolves it against the repo's history. A prefix shared by more than one commit is refused with the candidates, so give more digits.

# names only a commit. @ also accepts one, but only as a last resort: owner/pkg@1234567 is first read as a version, a range or a track, and as a commit only if none of those match. A hex string that happens to be a version or a track name therefore always means the version or track; use # to be sure you get a commit. The Cactarium always answers with the full id, as owner/pkg#<commit>, which is what CactUp records.

If a published version was frozen at exactly that commit, the reference simply names that version, and it is served like any version. Any other commit is read as the package is there, thorns and manifest, like a tip but pinned. Nobody reviewed it, so the same rule as for tips applies: a trusted package (the entry or its owner) is served; for others the site's setting decides, refusing such commits or serving them marked untrusted so CactUp warns and asks first.

@head and @master

A stack's @head and @master are described under Stacks. A package has them too: owner/pkg@head and owner/pkg@master both mean the package at the tip of its default branch, read when asked. The API returns that commit, with the thorns and claims found there. They follow the stacks' rule: served for a trusted package, and for others only when the site allows untrusted branch tips. Neither is ever a version, and neither is reviewed.
