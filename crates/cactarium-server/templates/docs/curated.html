Curated packages

Many repos, including most of the Einstein Toolkit's, have no cactarium.toml of their own yet. A curated package covers such a repo: Cactarium admins write its manifest, and the Cactarium keeps it instead of reading it from the repo. Everything else works as for any package. The page marks it curated: published by Cactarium admins for a repo whose authors haven't published it themselves.

A curated package is a stopgap. When the maintainers commit their own manifest, it is handed over to them.

Where its versions come from

  • Upstream tags. Tags named vX.Y.Z, or those matching the manifest's tag-pattern (such as ET_{major}_{minor}_v{patch}), from its since on. They are read and frozen exactly as for a registered package; see frozen commits. A new upstream tag goes through review unless the entry or its owner is trusted.
  • Commits. For a repo without usable tags, an admin names a version and the full commit id it stands for. The commit must be fetchable from the repo. These versions are frozen the same way, published at once, and marked curated on the Versions tab; the API gives them no tag and "curated": true.

For maintainers: taking it over

If your repo is on the Cactarium as a curated package and you'd like to maintain the entry yourself:

  1. Commit a cactarium.toml (see the reference) to your repo's default branch. Give it the same name as the curated package, and list the package's current owner, the part before the slash (such as et), in owners. If you'd like the entry moved under your own name or organization, list that as well.
  2. Ask a Cactarium admin to choose Use the repo's manifest for the package, and to move it to your namespace if you want that.

The hand-over keeps the package's name, its URL and every version already published. From then on the Cactarium reads your manifest at each new tag: its tag-pattern and since decide which tags are versions, and its owners must keep naming the entry's owner. The curated mark goes away.

For admins

Creating one

Under Admin, Curated, New curated package takes the owner namespace (cactarium by default, or an organization such as et), the repo's URL, and the overlay manifest: a cactarium.toml in the usual schema. Its owners may not be empty, but nothing checks it against the repo. The repo's existing tags become versions at once, vouched for by you.

format = 1

[package]
name = "carpetx"
owners = ["et"]
description = "CarpetX, the AMReX-based driver"
tag-pattern = "ET_{major}_{minor}_v{patch}"
since = "2026.5.0"

Each curated package's card has Add version: a version (1.0.0, or track:1.0.0) and a full commit id.

Many at once

just curate <admin> curate.toml creates or updates curated packages from a file that lists one [[package]] per repo, as the given admin:

[[package]]
owner = "et"
url = "https://github.com/EinsteinToolkit/ExternalLibraries-HDF5"
manifest = "manifests/hdf5.toml"   # relative to this file

[[package.version]]                 # optional: versions by commit
version = "2026.5.0"
commit = "…full commit id…"

Running it again updates the URL and manifest of packages that changed and adds missing versions. A package that has been handed over to its repo's manifest is left alone. tag-pattern and since belong in each manifest, not in this file.

Handing over

Use the repo's manifest checks the cactarium.toml on the repo's default branch: it must give the package's name and list its owner in owners. Then the overlay is dropped, the package stops being curated, its tag rule becomes the repo manifest's, and its tags are checked at once. To move the entry to the maintainers' namespace, use transfer under Admin, Entries.

A repo that moved

When a repo moves, say to another GitHub owner, Admin, Entries, move repo points the entry at the new URL, after checking that the new URL holds the same history: every frozen tag at the same commit, every commit-named version fetchable. A repo carrying several entries (a package, a stack, sims) moves as a whole: every entry on it is checked the same way, and they all move together in one transaction, or none does. The operator's just cli move-repo <admin> <owner/name> <new-url> does the same. A changed URL in a curate file gets the same check.

Re-reading invalid versions

A repo entry has no tag rule to switch: each tag is read by the manifest in its own commit (how). Admin, Entries offers, for every entry released from its repo that isn't curated:

  • Re-read invalid version: an invalid version, typed in, is read again at its frozen commit. Invalid versions were never served, so nothing depends on them: one that reads cleanly now becomes valid and is reviewed like a newly pushed tag (read from another tag naming exactly that version, such as a v1.0.0 beside the bare 1.0.0 it was frozen from, when the frozen tag still fails); one whose tag turns out not to be a version of the entry at all, read by the manifest in its commit (for instance, one frozen by an older Cactarium for a tag without the manifest), is removed and recorded so; one that still fails stays, and the reason is shown. just cli reread <admin> <owner/name> <version> does it from the command line. For curated packages, re-applying the overlay (Admin, Curated, or just cli reapply <admin> <owner/name>) plays this part.
  • Examine tag again: a tag listed under Tags not read as versions, typed in, loses its record and is examined again under the rules as they are now (and frozen if it is a version now). just cli reread <admin> <owner/name> --tag <tag> does it from the command line.

Curated stacks

Stacks need no special mechanism: keep a manifest repo of our own with the stack file, tag it, and register it like any repo.
